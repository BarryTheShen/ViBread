# ViBread slice 02 — circuit IR and schematic

**Research snapshot:** 2026-09-25. Claims about releases, stars, and last activity are observations from the linked registries/repos on this date; they are not promises that a project will still be maintained at hackathon submission time.

## 1) Scope

This slice covers the representation produced by the ViBread agent, browser schematic rendering, the small Arduino-kit module catalog, component/datasheet lookup, and existing electronics-design MCP servers. The target is a **checked, compact, board-aware description** of at most roughly 15 modules/parts which can feed ERC/static checks, SPICE/Wokwi/MCU simulation, an Arduino sketch, breadboard assembly steps, and physical verification.

The board assumption (Uno R3/Nano, ATmega328P) is not confirmed. The IR therefore treats the board as a first-class versioned part rather than hard-coding Uno pin numbers. Arduino's official A000066 Uno R3 datasheet/pinout is the starting source for the R3 descriptor ([datasheet](https://docs.arduino.cc/resources/datasheets/A000066-datasheet.pdf), [pinout](https://docs.arduino.cc/resources/pinouts/A000066-full-pinout.pdf)). An Uno R4 descriptor must instead use the RA4M1/R4 documentation ([official R4 datasheet](https://docs.arduino.cc/resources/datasheets/ABX00080-datasheet.pdf)); Nano R3 and Uno R3 share an ATmega328P family but do **not** share the same physical header geometry. ESP32 (3.3 V, boot-strapping/ADC restrictions) and Pico/RP2040 (3.3 V) require separate descriptors and validation rules, not aliases for Uno.

### Decision in one paragraph

**Build a small ViBread JSON IR and JSON-Schema/Zod validator; do not make KiCad, Wokwi, Circuit JSON, or an LLM-generated Python DSL the canonical representation.** Export to KiCad 10 `.kicad_sch` for professional rendering/ERC, Wokwi `diagram.json` for MCU simulation, SPICE for analog checks, and optionally Circuit JSON/tscircuit for browser/PCB artifacts. Build the browser semantic schematic viewer around our IR using SVG/React and `elkjs`; use `@wokwi/elements` for optional breadboard/module visuals and retain KiCad SVG as a downloadable artifact. The renderer should preserve the same IDs and pin/net diagnostics as the validator so a highlighted visual finding is not a second, stale data model.

## 2) Industry standard

### 2.1 What established tools actually use

Professionals commonly keep a **rich schematic source** in an EDA-native format, then generate specialized artifacts: a netlist/BOM, simulation netlist, PCB data, manufacturing outputs, and plots. KiCad 10 is the current open-source major release; its CLI documents schematic ERC, netlist export, and SVG export as separate automated operations ([KiCad 10 CLI manual](https://docs.kicad.org/10.0/en/cli/cli.html), [10.0 release](https://www.kicad.org/blog/2026/03/Version-10.0.0-Released/), [10.0.6 release](https://www.kicad.org/blog/2026/08/KiCad-10.0.6-Release/)). SPICE remains the standard simulation interchange for lumped analog circuits; an EDA's schematic is normally translated into a simulator-specific netlist rather than used as the simulator source. EDIF remains a formal, older interchange for hierarchical digital/netlist data, while Yosys JSON is a practical synthesis-tool interchange for RTL/gate-level digital designs. Circuit JSON, atopile, and SKiDL are modern code/data representations, but are not universal industry interchange standards.

A useful separation for ViBread is:

* **Intent IR:** compact, strict, board/module-aware, with evidence and uncertainty. This is what the LLM emits and the validator owns.
* **Schematic/document artifact:** KiCad `.kicad_sch` or our browser SVG. It carries human-readable symbol geometry and labels.
* **Connectivity/simulation artifacts:** KiCad netlist, SPICE, Wokwi diagram, firmware tests. Each deliberately loses information irrelevant to its consumer.
* **Assembly artifact:** a separate breadboard placement/step plan, linked to the same part/pin/net IDs. A netlist alone cannot describe a breadboard hole or a step-by-step action.

### 2.3 Concrete ViBread IR

Use a versioned JSON object validated with JSON Schema (or Zod in TypeScript), with `additionalProperties: false` at externally generated boundaries. Keep stable semantic IDs separate from generated SVG/KiCad UUIDs. Do not let the model emit arbitrary JavaScript/Python or filesystem paths.

```json
{
  "schemaVersion": "vibread.circuit/0.1",
  "designId": "moon-lamp-001",
  "board": {
    "family": "arduino-uno-r3",
    "partKey": "arduino.uno-r3",
    "mcu": "atmega328p",
    "logicVoltage": "5V",
    "source": "https://docs.arduino.cc/resources/datasheets/A000066-datasheet.pdf"
  },
  "parts": [
    {
      "id": "led1",
      "ref": "D1",
      "role": "indicator",
      "partKey": "generic.led-5mm",
      "variant": "red-through-hole",
      "value": { "nominal": 0.01, "unit": "A", "tolerance": null },
      "pins": [
        { "id": "a", "name": "A", "number": "1", "electricalType": "passive" },
        { "id": "k", "name": "K", "number": "2", "electricalType": "passive" }
      ],
      "evidence": [{ "url": "https://docs.wokwi.com/parts/wokwi-led", "kind": "pinout", "confidence": "reference" }]
    },
    {
      "id": "r1",
      "ref": "R1",
      "role": "current-limit",
      "partKey": "generic.resistor",
      "variant": "through-hole",
      "value": { "nominal": 220, "unit": "ohm", "tolerance": { "value": 0.05, "unit": "ratio" }, "powerRating": "0.25W" },
      "pins": [
        { "id": "1", "name": "1", "number": "1", "electricalType": "passive" },
        { "id": "2", "name": "2", "number": "2", "electricalType": "passive" }
      ]
    }
  ],
  "nets": [
    { "id": "gnd", "name": "GND", "kind": "ground", "members": [{ "partId": "board", "pinId": "GND" }] },
    { "id": "led-drive", "name": "LED_DRIVE", "kind": "signal", "members": [{ "partId": "board", "pinId": "D13" }, { "partId": "r1", "pinId": "1" }] },
    { "id": "led-k", "name": "LED_K", "kind": "signal", "members": [{ "partId": "r1", "pinId": "2" }, { "partId": "led1", "pinId": "a" }] }
  ],
  "boardPins": {
    "D13": { "arduinoLabel": "D13", "mcuPort": "PB5", "capabilities": ["digital", "spi-sck", "led_builtin"], "voltage": "5V", "maxSourceCurrent": "20mA" },
    "GND": { "arduinoLabel": "GND", "capabilities": ["ground"], "voltage": "0V" }
  },
  "layoutHints": {
    "schematic": [{ "partId": "board", "group": "controller", "order": 0 }, { "partId": "led1", "group": "indicator", "side": "right" }],
    "breadboard": [{ "partId": "board", "anchor": "top-left" }, { "partId": "led1", "row": 12, "column": 15, "orientation": "vertical" }]
  },
  "assembly": { "steps": [{ "id": "s1", "action": "place", "partId": "led1", "verify": ["pins-visible"] }] },
  "provenance": { "generatedBy": "vibread-agent", "intentText": "...", "assumptions": ["board identified as Uno R3"] }
}
```

Required field groups:

1. `schemaVersion`, `designId`, provenance, user intent, assumptions, and evidence links.
2. `board`: family/variant, MCU, logic voltage, power limits, fixed/reserved pins, aliases (`D13`, `PB5`, physical header position), capabilities (`digital`, `PWM`, `ADC`, `I2C`, `SPI`, `UART`, interrupt), and board-specific forbidden/boot pins.
3. `parts`: stable ID, reference, role, canonical `partKey`, exact variant/MPN when known, module-vs-discrete classification, value and tolerance, operating/absolute limits, footprint/package only when useful, and source evidence/confidence.
4. `pins`: stable ID, display name, physical number, role (`VCC`, `GND`, `SIG`, `ANODE`, `CATHODE`, `TRIG`, `ECHO`, etc.), electrical type (`input`, `output`, `bidirectional`, `power-input`, `power-output`, `passive`, `open-collector`, `tri-state`, `no-connect`), voltage/current limits, protocol/active-low metadata, and optional internal equivalent pin.
5. `nets`: stable ID/name, members `(partId,pinId)`, kind (`power`, `ground`, `signal`, `bus`, `contact`), voltage/current/domain expectations, pull-up/down, and whether an external supply is required.
6. `moduleVariants`: aliases and substitution constraints. A `HC-SR04` module and a 3.3 V ultrasonic module must not silently share the same pin/electrical contract. Model `16x2-I2C-LCD` as an interface plus backpack variant, not as one universal 16-pin part.
7. `layoutHints`: schematic grouping/order/side/anchor; breadboard row/column/rail/orientation; assembly step IDs and required verification observations. Hints are never connectivity truth.
8. `exports`: mapping to KiCad symbol, Wokwi type/pin names, SPICE model/subcircuit, Arduino library/protocol, and Circuit JSON adapter version. Export mappings are generated/validated, not LLM-authored opaque paths.

Minimum deterministic validation before any export: unique IDs and refs; every net member resolves; every part pin appears at most once per net; board aliases resolve to the selected board descriptor; required power/GND pins are connected; no accidental output-output or incompatible voltage-domain connection; tolerances/units parse; variant has evidence; all unknowns become explicit warnings/errors. ERC severity can be stricter than KiCad's generic pin matrix for Arduino rules (GPIO current, 5 V-to-3.3 V input, servo/relay supply, WS2812 current, and floating inputs).

### 2.4 Curated Arduino-kit module data plan

The first-party manifest should contain **facts and links, not copied graphics**. Each row stores `partKey`, exact variant/MPN when known, canonical pin roles, electrical limits/ranges, protocol behavior, `sourceUrl`, `sourceKind`, `retrievedAt`, optional PDF hash, `confidence`, and a `licenseNote`. A generic family row is allowed only when the field is explicitly a range/unknown; it must not silently stand in for a module clone. Wokwi pin names are useful for simulation adapters, but manufacturer datasheets or board-vendor documentation remain the authority for real hardware.

The curated manifest wins over a remote catalog for the demo: catalog results can select an exact MPN, but the manifest controls pin semantics, board compatibility, variant warnings, and simulation/assembly mappings.

## 6) Integration notes & gotchas for our stack

### 6.1 TypeScript/Bun/Linux

* Keep the canonical types in TypeScript and emit JSON Schema for model tool schemas. Use integer/decimal-plus-unit parsing rather than JavaScript floating-point equality for resistor values/tolerances.
* Pin exact npm versions and retain an SPDX/license report. `elkjs` is EPL-2.0 (and current npm metadata reports an EPL/GPL alternative); this is compatible with a permissive app if notices are retained, but do not silently relicense it. `circuit-json`/`circuit-to-svg` report ISC; `@tscircuit/schematic-viewer` is MIT; Wokwi Elements is MIT. Confirm transitive licenses in the lockfile before shipping ([elkjs metadata](https://registry.npmjs.org/elkjs), [circuit-json metadata](https://registry.npmjs.org/circuit-json), [Wokwi Elements metadata](https://registry.npmjs.org/@wokwi/elements)).
* Execute `kicad-cli`, `ngspice`, and `wokwi-cli` only through fixed argument arrays with timeouts, resource limits, output-size caps, and no shell interpolation. Capture stdout/stderr/version and hash inputs/outputs for reproducibility.
* A minimal container can install KiCad 10 CLI, but verify the image actually contains symbol libraries and fonts. Do not assume KiCad's bundled Python API is present on Linux; prefer CLI for schematic/ERC. KiCad format versions move with major releases; generate from a known template and run the installed CLI rather than hand-coding a guessed file header.
* Browser output is reached through an SSH tunnel. Do not make the browser call localhost on the user's laptop for renderer data; return relative artifact URLs through the tunneled ViBread server. USB serial remains a separate browser/Web Serial concern.

### 6.2 Board and module semantics

* Uno R3/Nano: Arduino labels must map through a board descriptor to ATmega328P ports and physical header positions. D13 is also SPI SCK/built-in LED on Uno R3; D0/D1 are UART; A4/A5 are I2C. These are capabilities, not permission to use all functions simultaneously.
* Uno R4: RA4M1 and changed peripheral/analog/DAC mapping require a different descriptor; an R3-generated sketch/netlist is unsafe. Reject a design if the board is ambiguous.
* ESP32: use 3.3 V limits and reserve strapping/flash pins according to the selected module; never assume “Arduino pin number” means the same electrical resource.
* Pico: 3.3 V GPIO and different ADC/I2C/SPI mappings; a 5 V HC-SR04 Echo or 5 V LCD must trigger a level-shift/power warning.
* Modules are not universal just because their silkscreen names match. HC-SR04 revisions differ in supply/Echo behavior; DHT11/22 require different timing/range assumptions; SSD1306 boards can be I2C or SPI and have address/configuration variants; I2C LCD backpacks can use PCF8574 or MCP23008 and different pin mappings; relay modules can be active-low, isolated, or share grounds; servos need a separate supply/current budget; WS2812 current scales with pixel count.
* Represent active-low, open-drain/open-collector, tri-state, pull-up, protocol, and power-domain facts in pins/interfaces. A generic `input`/`output` pair is insufficient for ERC or generated tests.

### 6.3 Rendering and accessibility

* Put net names on long/ambiguous nets and display pin names plus Arduino aliases. Color is supplementary; use patterns/labels for red-green color blindness and monochrome export.
* Click a part/pin/net to show its source evidence, current assumptions, validation findings, and physical assembly steps. On phone, collapse symbol properties into a bottom sheet instead of shrinking labels.
* Keep schematic (logical connectivity) and breadboard (physical placement) as tabs/views over one IR. Do not draw a wire in the browser if it is not in a validated net; visual layout hints may be stale and must be marked.
* ELK's graph layout is not an electronics router. Constrain board left, power rails top/bottom, inputs left, outputs right, and group interfaces; then post-process orthogonal routes and run an overlap/label check.

### 6.4 API/catalog licensing

* **Nexar/Octopart:** Official API is GraphQL at `api.nexar.com/graphql`, OAuth 2.0, with search/inventory/pricing/datasheets ([technical docs](https://www.altium.com/documentation/altium-developer-center/octopart/api), [authorization](https://www.altium.com/documentation/altium-developer-center/octopart/api/authorization)). API terms grant a revocable application license and restrict publishing/self-hosting/caching (Nexar terms [here](https://nexar.com/api/legal)); do not mirror catalog data in the public repo. Use only with an approved key and a server-side wrapper.
* **DigiKey:** Product Information V4 supports product/keyword search and OAuth; API docs describe client credentials/headers and rate limits ([portal](https://developer.digikey.com/products/product-information-v4), [OAuth](https://developer.digikey.com/tutorials-and-resources/oauth-20-2-legged-flow)). Credentials belong in server secrets, never browser/IR.
* **Mouser:** Official Search API exists at [Mouser API Search](https://www.mouser.com/en/api-search/), but automated access was blocked during this research and exact current limits/fields were not independently verified **[UNVERIFIED]**. Treat as optional and link to its product/datasheet page rather than caching responses.
* **LCSC/JLCPCB:** LCSC documents REST-style catalog endpoints ([API instruction](https://www.lcsc.com/docs/openapi/index.html)); JLCPCB advertises a Components API but requires developer access/application ([platform](https://api.jlcpcb.com/), [access notice](https://jlcpcb.com/help/article/jlcpcb-online-api-available-now)). Community mirrors such as `jlcsearch` can be useful but are not an authoritative license/availability contract ([repo](https://github.com/tscircuit/jlcsearch)). Do not scrape or ship a catalog dump during the hackathon.
* **Datasheet PDFs:** store manufacturer/official distributor URL, MPN, revision/date, and optional SHA-256; do not redistribute PDFs unless their terms allow it. Extracted facts get `sourceUrl`, `page/section`, `retrievedAt`, and `confidence`. A human-visible “verify datasheet” link is more valuable than a copied image.

## 7) Risks & unknowns

1. **Board ambiguity:** Uno R3/Nano vs Uno R4/ESP32/Pico changes voltage, pins, boot constraints, and firmware libraries. Make board selection a required confirmation or an explicit low-confidence assumption; never silently compile a different target.
2. **Module variance:** Names such as “SG90,” “HC-SR04,” “DHT22,” “16x2 I2C LCD,” “relay module,” and “KY-023” identify families/clone modules, not one guaranteed pinout/spec. Require variant evidence and provide a “physically confirm silkscreen/pin order” step.
3. **Model-vs-real gap:** Wokwi and SPICE may omit GPIO current limits, connector faults, EMI, servo startup current, relay isolation, sensor timing, or breadboard shorts. Report simulation coverage and uncertainty instead of a green “passed.”
4. **KiCad generation fragility:** `.kicad_sch` is versioned, symbol UUID/geometry-heavy, and easy to corrupt by text editing. Use a known KiCad 10 template, a constrained generator, CLI open/ERC/export smoke checks, and do not expose arbitrary file mutation to the LLM.
5. **Renderer correctness:** A visually neat graph can still hide a dangling pin or joined net. Renderer consumes normalized IR only and overlays validator IDs; tests should compare net membership independently from SVG snapshots.
6. **License contamination:** KiCad/Fritzing graphics and catalog/datasheet content have CC/share-alike or provider-specific restrictions. Keep curated facts and links, use own simple symbols or permissively licensed dependencies, and retain third-party notices. Do not copy competitor source or an existing MCP/application.
7. **Supply-chain/security:** MCP packages and CLIs can download code, create venvs, update themselves, or invoke external tools. Pin versions/hashes, run workers with no write access outside a per-job directory, disable auto-update, and require explicit permission for writes/flash/orders.
8. **Catalog freshness/terms:** Stock/pricing, URLs, API limits, and data rights change. Catalog search is optional and must return timestamps/partial results; exact MPN + datasheet evidence outranks an LLM's remembered spec.
9. **Time/complexity:** A general PCB autorouter, complete Fritzing importer, or all-Arduino-board library is out of scope for a 36-hour demo. Seed common descriptors, prove one Uno R3 path end-to-end, and fail with actionable unknowns for everything else.
10. **No independent verification yet:** This is research only; actual KiCad 10 installation, the chosen Wokwi CLI/account mode, and the final MCP SDK transport should be smoke-tested by the main build agent before selecting dependencies.
