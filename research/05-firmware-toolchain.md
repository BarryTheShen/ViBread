# ViBread research — firmware toolchain (slice 05)

**Research date:** 2026-09-25.  **Target:** Arduino Uno R3/Nano first; keep the board profile explicit because Uno R4, ESP32, and RP2040 use different cores, pin maps, timers, and simulators.

## 1) Scope

This slice covers the firmware side of ViBread: reproducible compilation and artifact collection; Arduino/PlatformIO MCP candidates; compiler/static diagnostics; code-to-netlist pin extraction; host, simulated, and hardware tests; common Arduino library versions/licenses; and deterministic self-test firmware generation.

The recommendation below assumes a server receives source generated by an LLM and must return evidence, not merely a compiler exit code. The server must never expose a generic shell tool: all operations use a fixed executable plus validated argument schemas, workspace confinement, bounded output, timeouts, and explicit permission for any upload or hardware write.

**Evidence boundary.** Release/version values and repository activity are live observations on the date above. Anything marked **[UNVERIFIED]** needs a final check immediately before packaging. Libraries and MCP servers may be used as dependencies/tools, but ViBread application code and its self-test generator must be written independently; the prior-art examples below are design references only.

## 2) Industry standard

### 2.1 What established Arduino workflows use

* **Arduino CLI is Arduino's canonical build service.** Arduino IDE 2.x and Arduino Cloud use Arduino CLI for board/core/library management and compilation; Arduino documents three integration pillars: CLI, gRPC daemon, and Go embedding ([official integration options](https://arduino.github.io/arduino-cli/1.5/integration-options/)). The CLI itself is GPL-3.0 ([license](https://raw.githubusercontent.com/arduino/arduino-cli/master/LICENSE.txt)); invoking its unmodified binary is preferable to embedding its Go packages in a TypeScript application.
* **PlatformIO is the broader multi-board engineering/build/test environment.** PlatformIO Core is Apache-2.0 and advertises multi-platform builds, dependency management, static analysis, and unit testing ([PyPI metadata/license](https://pypi.org/pypi/platformio/json), [project configuration](https://docs.platformio.org/en/latest/projectconf/index.html)). It is a strong professional alternative when one repository targets AVR, ESP32, STM32, RP2040, Renesas, etc.; it is not needed just to compile one Arduino sketch.
* **Reproducibility means pinning board/core/toolchain/library versions.** Arduino CLI accepts `PACKAGER:ARCH[@VERSION]`, e.g. `arduino-cli core install arduino:avr@1.8.8` ([core install](https://arduino.github.io/arduino-cli/1.5/commands/arduino-cli_core_install/)). PlatformIO recommends exact package versions or VCS tags rather than unbounded latest dependencies ([dependency management](https://docs.platformio.org/en/latest/librarymanager/dependencies.html)). Commit a ViBread lock record containing CLI version, FQBN, core release, tool packages, library names/versions, analyzer versions, simulator version, and SHA-256 hashes.
* **Unit + integration + HIL is the normal layering.** PlatformIO's test runner explicitly supports host (native), embedded target, or both, with serial result collection ([unit-testing overview](https://docs.platformio.org/en/latest/advanced/unit-testing/index.html)). Use host tests for pure logic, simulator scenarios for MCU/peripheral behavior, and a small physical test suite for the final board/wiring. A simulator result must not be presented as proof that a breadboard is wired correctly.

### 2.2 Arduino CLI 1.5.1 on Linux x64

The current stable release observed from the official release page was **arduino-cli v1.5.1**, released 2026-06-05, with a Linux 64-bit tarball ([release](https://github.com/arduino/arduino-cli/releases/tag/v1.5.1), [installation](https://arduino.github.io/arduino-cli/1.5/installation/)). The exact installation used for this research was:

```bash
mkdir -p /opt/arduino-cli/1.5.1
curl -fsSL https://downloads.arduino.cc/arduino-cli/arduino-cli_1.5.1_Linux_64bit.tar.gz \
  | tar -xz -C /opt/arduino-cli/1.5.1
/opt/arduino-cli/1.5.1/arduino-cli version
# arduino-cli  Version: 1.5.1 Commit: 01f3d4f2b Date: 2026-06-05T10:22:17Z
```

For a disposable/containerized installation, the official versioned install script is also supported:

```bash
curl -fsSL https://raw.githubusercontent.com/arduino/arduino-cli/master/install.sh \
  | sh -s 1.5.1
```

Do not pipe an unpinned `latest` script into a production build image. Set all Arduino directories to job-owned paths so one user/job cannot mutate another job's indexes or libraries:

```bash
export ARDUINO_DIRECTORIES_DATA="$JOB_DIR/.arduino15"
export ARDUINO_DIRECTORIES_USER="$JOB_DIR/Arduino"
export XDG_CACHE_HOME="$JOB_DIR/.cache"
arduino-cli config init
arduino-cli update                    # cores and libraries indexes
arduino-cli core install arduino:avr  # requested/latest index release; not reproducible
arduino-cli core install arduino:avr@1.8.8  # ViBread lockfile choice
arduino-cli core list
```

The data/user/build-cache defaults and `build_cache` TTL/purge settings are documented in [configuration](https://arduino.github.io/arduino-cli/1.5/configuration/). Use `ARDUINO_DIRECTORIES_DATA`, `ARDUINO_DIRECTORIES_USER`, and an explicit `build_cache.path` (or `XDG_CACHE_HOME`) in the worker rather than relying on `$HOME`.

**FQBN caveat.** `arduino:avr:uno` is correct for Uno R3 (ATmega328P), as documented by [Uno R3 hardware documentation](https://docs.arduino.cc/hardware/uno-rev3). Do not infer the FQBN from the product name alone; enumerate/resolve it with `arduino-cli board listall` and persist the selected profile. The official FQBN grammar is [here](https://arduino.github.io/arduino-cli/1.5/platform-specification/).

### 2.3 Compile commands, flags, artifacts, and diagnostics

Recommended server command (use documented `--json`; v1.5.1 also accepted the user's `--format json` spelling, but it is not shown in `compile --help`):

```bash
arduino-cli compile \
  --fqbn arduino:avr:uno \
  --json \
  --warnings all \
  --output-dir "$JOB_DIR/artifacts" \
  --build-property 'build.extra_flags=-DVIBREAD_TEST=1' \
  --build-property 'compiler.cpp.extra_flags=-Wall -Wextra' \
  "$JOB_DIR/sketch/Blink"
```

The official `compile` reference documents `--build-property` (repeatable), `--warnings {none,default,more,all}`, `--build-path`, `--output-dir`, `--export-binaries`, `--jobs`, `--clean`, `--only-compilation-database`, and JSON output ([compile command](https://arduino.github.io/arduino-cli/1.5/commands/arduino-cli_compile/)). `--warnings all` maps to GCC `-Wall -Wextra`; verify the effective commands with `--verbose` because platform recipes can add/override flags. Treat third-party library warnings separately from generated application warnings; avoid global `-Werror` on an LLM sketch until the selected libraries are known-good.

**Observed JSON shape (v1.5.1).** A successful invocation returned top-level keys:

```json
{
  "compiler_out": "Sketch uses ...\\nGlobal variables use ...\\n",
  "compiler_err": "",
  "builder_result": {
    "build_path": "/.../arduino/sketches/<hash>",
    "executable_sections_size": [
      {"name": "text", "size": 922, "max_size": 32256},
      {"name": "data", "size": 9, "max_size": 2048}
    ],
    "board_platform": {"id": "arduino:avr", "version": "1.8.8", "install_dir": "..."},
    "build_platform": {"id": "arduino:avr", "version": "1.8.8", "install_dir": "..."},
    "build_properties": ["..."],
    "diagnostics": []
  },
  "upload_result": {},
  "success": true,
  "error": ""
}
```

A deliberate warning + compile error produced `builder_result.diagnostics[]` entries with:

```json
{
  "severity": "WARNING" | "ERROR",
  "message": "compiler text without the file prefix...",
  "file": "/workspace/sketch/Blink.ino",
  "line": 3,
  "column": 40,
  "context": [{"message": "In function ...", "file": "..."}],
  "notes": []
}
```

On failure, the process exited 1, `success` was false, `error` was `"Error during build: exit status 1"`, and `compiler_err` still contained raw GCC output. Parse both structured diagnostics and raw streams; preserve `context`/`notes`, normalize severity, and never make a regex over the human `Sketch uses` line the source of truth. The corresponding protobuf fields (`BuilderResult`, `CompileDiagnostic`, `CompileResponse` stream, and `ArduinoCoreService.Compile`) are specified in the [gRPC protocol reference](https://arduino.github.io/arduino-cli/1.5/rpc/commands/).

**Artifact paths.** With `--output-dir`, v1.5.1 wrote `Sketch.ino.elf`, `Sketch.ino.hex`, `Sketch.ino.eep`, `Sketch.ino.with_bootloader.bin`, and `Sketch.ino.with_bootloader.hex` directly into that directory. Without it, `builder_result.build_path` pointed under the Linux build cache (`$XDG_CACHE_HOME/arduino/sketches/<hash>`). `--export-binaries` followed the documented “export to sketch folder” behavior by creating `sketch/build/arduino.avr.uno/` in the tested CLI; use `--output-dir` for deterministic server artifacts. The ELF is required by simulators/debuggers; the HEX is the normal flash image. Arduino's build-process documentation explains that the final AVR output is Intel HEX and that object/dependency files are reused when timestamps/dependencies are unchanged ([build process](https://arduino.github.io/arduino-cli/1.5/sketch-build-process/)).

`--only-compilation-database` is useful for analyzers; archive the resulting `compile_commands.json` with the build record. It still runs pre-hooks, so do not permit arbitrary project hooks in an untrusted workspace.

### 2.4 Library index, dependencies, and pinning

```bash
arduino-cli lib update-index
arduino-cli lib search --format json 'name="Adafruit SSD1306"'
arduino-cli lib install 'Adafruit SSD1306@2.5.17'
arduino-cli lib list --format json
```

The exact `LIBRARY[@VERSION]` syntax and dependency installation are documented by [lib install](https://arduino.github.io/arduino-cli/1.5/commands/arduino-cli_lib_install/); search qualifiers and JSON output are documented by [lib search](https://arduino.github.io/arduino-cli/1.5/commands/arduino-cli_lib_search/). Arduino library metadata uses `library.properties`; dependency constraints may be exact or ranges ([library specification](https://arduino.github.io/arduino-cli/1.5/library-specification/)). For ViBread, resolve the requested library name once, reject ambiguous/fuzzy matches, install exact versions plus dependencies, and save the resulting `library.properties`, archive URLs/checksums, and lock manifest. Do not silently upgrade on a later compile.

### 2.5 gRPC daemon, speed, cache, and concurrency

Run a local daemon only if its persistent process/index state is worth the integration cost:

```bash
arduino-cli daemon --port 50051 --max-grpc-recv-message-size 16777216
```

The official daemon supports TCP gRPC, default `127.0.0.1:50051`, debug logging/filtering, and a 16 MiB default maximum receive message ([daemon command](https://arduino.github.io/arduino-cli/1.5/commands/arduino-cli_daemon/)). The client flow is `Create` → streamed `Init` → `PlatformSearch`/`Library*`/`Compile`; `Compile` is server-streaming and returns progress plus `BuilderResult` ([integration options](https://arduino.github.io/arduino-cli/1.5/integration-options/), [protocol](https://arduino.github.io/arduino-cli/1.5/rpc/commands/)). Arduino calls gRPC high-performance and language-agnostic, but no official end-to-end warm-compile benchmark was found. Do not promise a speedup: the compiler, library discovery, and disk cache still dominate. A Node client would need generated protobuf bindings or a gRPC/protobuf adapter; the CLI subprocess is lower setup for this weekend.

**Measured local smoke timings (not a universal benchmark).** After `arduino:avr@1.8.8` was already installed, an Uno sketch built through a fresh explicit output directory in about 0.353 s and repeated in about 0.312 s. PlatformIO 6.2.0 took 13.73 s for its first Uno build because it downloaded `atmelavr@5.3.0`, toolchain/framework, and Unity, then about 0.618 s wall time on a warm build (PlatformIO reported 0.262 s for the build target). These numbers include this machine's filesystem/cache state and should be replaced by ViBread's own p50/p95 benchmark.

**Concurrency warning (reproduced).** Two simultaneous `arduino-cli compile --clean --output-dir SAME_DIR` calls for the same sketch/FQBN caused one to pass and one to fail with linker `undefined reference to main`; the shared build directory was left with artifacts. Arduino's `BuildCache.GetOrCreate()` only creates the key directory and rewrites `.last-used`; the v1.5.1 source has no cross-process lock around shared sketch/core artifact writes ([source](https://github.com/arduino/arduino-cli/blob/v1.5.1/internal/buildcache/build_cache.go)). The docs describe TTL/purge but do not guarantee concurrent writers ([configuration](https://arduino.github.io/arduino-cli/1.5/configuration/)). Therefore:

1. give every compile a unique job workspace and `--output-dir`/`--build-path`;
2. serialize first-time core/tool/library installation globally;
3. serialize compiles keyed by `(sketch content hash, FQBN, flags, dependency lock)` if sharing a cache, or disable shared writes and use per-job caches;
4. never run `--clean` against a shared path;
5. use atomic rename when publishing an artifact record; and
6. if using a daemon, still enforce the ViBread scheduler lock—the daemon does not make the underlying build path multi-writer safe.

## 4) Recommendations per sub-area (USE / WRAP / BUILD)

| Sub-area | Decision | Recommendation and rationale |
|---|---|---|
| Primary Uno compiler/artifacts | **USE** | Pin and invoke `arduino-cli` v1.5.1 as an external binary; install `arduino:avr@1.8.8` and use explicit `--output-dir`, `--json`, `--warnings all`, `--only-compilation-database` as needed. This is the Arduino-supported path and returns structured diagnostics/artifact metadata. |
| Long-lived compiler process | **WRAP** | Optionally supervise one localhost-only `arduino-cli daemon` per worker. Wrap only the generated RPC methods needed (`Version`, `Create`, `Init`, `Compile`, `Library*`, `Platform*`); retain ViBread's job locks because daemon/cache does not guarantee multi-writer safety. For the hackathon, subprocess CLI is lower-risk; benchmark daemon before adopting it. |
| PlatformIO | **WRAP** | Use PlatformIO 6.2.0 for the test/static-analysis environment and future multi-board builds, not as the primary Uno compiler. It brings a Python/SCons package graph and its own AVR framework package (`atmelavr@5.3.0`, `framework-arduino-avr@5.4.0` in the smoke run), so using both compilers can produce subtly different firmware. |
| Compiler warnings | **USE** | Gate `--warnings all` and preserve JSON diagnostics; add `-Wall -Wextra` explicitly only when the selected board recipe needs it. Treat warning policy as part of test spec and expose warnings separately from hard errors. |
| Cppcheck | **USE** | Run against the exact compile database with `--platform=avr8`, the effective C++ standard, `--enable=warning,performance,portability`, `--xml`, and a cache directory. PlatformIO's `pio check` supports Cppcheck by default, `--json-output`, `--fail-on-defect`, filters, and `--skip-packages` ([command](https://docs.platformio.org/en/latest/core/userguide/cmd_check.html), [Cppcheck integration](https://docs.platformio.org/en/latest/advanced/static-code-analysis/tools/cppcheck.html)). Cppcheck is GPL-3.0 ([license](https://github.com/danmar/cppcheck/blob/main/COPYING)); invoke it as a tool and include notices if distributed. It complements tests and does not prove intended behavior ([Cppcheck manual](https://cppcheck.sourceforge.io/manual.pdf)). |
| clang-tidy | **WRAP** | Use only for portable/application logic with a compilation database; choose bounded checks (`bugprone-*`, `clang-analyzer-*`, selected `performance-*`/`readability-*`) and do not use `--fix` on LLM output automatically. AVR headers/`avr/io.h`, GCC builtins, and `-mmcu` are known trouble spots for Clang tooling ([clangd AVR issue](https://github.com/clangd/clangd/issues/528), [PlatformIO Clang-Tidy docs](https://docs.platformio.org/en/latest/advanced/static-code-analysis/tools/clang-tidy.html)). PlatformIO's integration supplies project/framework flags, but isolate hardware glue from host-analyzable logic. |
| arduino-lint | **USE** for packaging only | It validates Arduino project structure/metadata/specification and Library Manager rules; it deliberately focuses on structure rather than code ([official docs](https://arduino.github.io/arduino-lint/latest/), [rules](https://arduino.github.io/arduino-lint/latest/rules/)). Run `arduino-lint --format json` on any generated reusable library, not as a replacement for compiler/static analysis. It is GPL-3.0 ([license](https://github.com/arduino/arduino-lint/blob/main/LICENSE.txt)). |
| Pin extraction | **BUILD** | Build a small, deterministic extractor over a syntax tree plus board profile. Recognize constant `pinMode`, `digitalRead/Write`, `analogRead/Write`, `tone`, `attachInterrupt`, `Servo.attach`, `Wire/SPI` setup, and constant constructor arguments. Emit source spans and confidence; mark dynamic values/macros/direct register accesses unknown. Use compile database/preprocessed `#line` output for context, but do not claim semantic certainty from regex. `tree-sitter-cpp` is MIT and supplies a C++ grammar ([repo](https://github.com/tree-sitter/tree-sitter-cpp)); AST parsing alone still needs ViBread's constant evaluator. |
| Runtime pin observation | **USE + BUILD adapter** | Observe actual AVR `DDR/PORT/PIN` writes in simulation. simavr supports IO ports, timers, interrupts, ADC, I2C, SPI, UART and VCD traces ([repo/docs](https://github.com/buserror/simavr), [VCD manual](https://fabricesalvaire.github.io/simavr/doxygen/group__sim__vcd__file.html)); `avr8js` exposes a TypeScript AVR CPU/GPIO core and listeners but requires ViBread to supply external hardware models ([repo](https://github.com/wokwi/avr8js)). Runtime coverage is evidence for exercised paths, not a proof that unexecuted branches never touch a pin. |
| Host tests | **USE** | Use PlatformIO `native` + Unity 2.6.1 (or GoogleTest 1.18.0 for a separately maintained C++ logic module). Unity is MIT, tiny, runs native and embedded, and PlatformIO has an official runner ([Unity docs](https://docs.platformio.org/en/latest/advanced/unit-testing/frameworks/unity.html), [license](https://github.com/ThrowTheSwitch/Unity/blob/master/LICENSE.txt)). GoogleTest is BSD-3-Clause and current README advertises 1.18.0 ([repo](https://github.com/google/googletest), [license](https://github.com/google/googletest/blob/main/LICENSE)); PlatformIO's GoogleTest embedded support is limited to ESP8266/ESP32 ([docs](https://docs.platformio.org/en/latest/advanced/unit-testing/frameworks/googletest.html)), so use it primarily on host. |
| On-device unit framework | **WRAP** | AUnit (MIT, v1.7.1 from 2023) and ArduinoUnit (MIT, Arduino-focused serial runner) are valid for small target-side checks, but they consume flash and depend on serial parsing. AUnit itself recommends native/EpoxyDuino for faster CI and target runs for architecture-specific checks ([AUnit README](https://github.com/bxparks/AUnit)); ArduinoUnit documents embedded and “en vitro” execution ([repo](https://github.com/mmurdoch/arduinounit)). Do not make either the only proof for LLM behavior. |
| Arduino mocks | **WRAP selectively** | ArduinoFake is MIT and provides native stubs/verifications ([repo](https://github.com/FabioBatSilva/ArduinoFake)), but its last stable release is old and it cannot model electrical contention/timers/peripherals. Prefer tiny ViBread-owned HAL interfaces plus Unity tests; use ArduinoFake only for a narrow host test if it saves time. |
| MCU behavior simulation | **USE** Wokwi when token exists; **USE** simavr/avr8js otherwise | Wokwi automation scenarios are convenient YAML but explicitly alpha and cloud-token/plan dependent. simavr is local Linux and integrates with PlatformIO (`pio test --without-uploading`) ([PlatformIO simavr docs](https://docs.platformio.org/en/latest/advanced/unit-testing/simulators/simavr.html)); it is GPL-3.0 ([COPYING](https://github.com/buserror/simavr/blob/master/COPYING)). `avr8js` is MIT and TS-native but requires writing peripheral glue. For a 36-hour build, a small scenario adapter over one simulator is safer than supporting all three. |
| Library selection | **USE** Arduino Library Manager with lockfile | Resolve exact names/versions and dependencies once. Avoid ambiguous or stale libraries; see the table in §6. NewPing's current v1.9.7 header grants use-as-is but forbids forks/derivatives, and LiquidCrystal I2C 1.1.2 has no license file in the installed archive while its GitHub repository is archived—do not make either a default generated dependency. |
| Netlist cross-check | **BUILD** | Static extraction should raise high-confidence conflicts (one pin declared output to two incompatible nets, I2C/SPI pin collision, pin reserved by a timer library); runtime simulation should add exercised evidence. It must report “unknown/dynamic” instead of silently accepting unresolved calls. |
| Deterministic physical self-test | **BUILD** | Generate a separate self-test sketch from netlist + board profile, with safe pin matrix cases, expected JSON lines, fixture requirements, series-resistor/current limits, and cleanup. Existing continuity testers demonstrate the idea but are fixed-jig sketches, not a generic netlist compiler (see §7). |
| ViBread firmware MCP | **BUILD** | Existing servers lack the combined compile → static → simulator → pin cross-check → self-test contract and ViBread permission modes. Build a narrow server over the pinned CLIs/libraries rather than cloning an MCP candidate. |

## 5) BUILD: proposed firmware MCP server

**Name:** `vibread-firmware` (stdio for Claude Code/local agent; optional localhost Streamable HTTP only behind an authenticated ViBread session).

**Global contract:** every request carries a `workspace_id` and immutable source/netlist/test-spec snapshot hash. Paths are server-owned IDs, never caller-selected executable paths. Tool outputs are bounded structured JSON with `status`, `summary`, `diagnostics`, `warnings`, `artifacts`, `nextActions`, and `provenance` (tool versions, FQBN, lock hash, simulator mode). No `run_command`, `shell`, arbitrary compiler flags, arbitrary upload path, or arbitrary environment map.

| Tool | Inputs (sketch) | Outputs (sketch) | Backing tool |
|---|---|---|---|
| `firmware_environment` | `{boardProfileId, fqbn?, refreshIndexes?: boolean}` | CLI/PlatformIO versions, installed core/tool versions, resolved FQBN, library index status; no writes unless separately approved | Arduino CLI `version`, `core list`, `board details`; PIO `--version` |
| `firmware_compile` | `{snapshotId, boardProfileId, libraryLock, warningPolicy, compilerDefines?, clean?: boolean}` | `{buildId, success, diagnostics[], memory:{flash,ram}, artifacts:{elf,hex,eep,bin}, compileCommandsArtifact, toolchain}` | Arduino CLI `compile --json --output-dir`; optional daemon `Compile` |
| `firmware_static_check` | `{buildId, analyzers:["cppcheck","clang-tidy","arduino-lint"], policy}` | `{diagnostics[], counts, exitPolicy, reports}` with file/line/column/severity/tool | Cppcheck, clang-tidy, arduino-lint; PlatformIO `pio check` adapter |
| `firmware_test` | `{buildId, testSpecId, mode:"native"|"simavr"|"avr8js"|"wokwi", timeoutMs}` | `{cases[], passed, failed, serialLogArtifact, tracesArtifact, simulatorVersion}` | PlatformIO Unity/native, simavr, avr8js, optional Wokwi CLI |
| `firmware_extract_pins` | `{buildId, sourceSnapshot, boardProfileId}` | `{uses:[{pin,operation,constantValue,sourceSpan,confidence}], buses, timers, unknowns[]}` | Tree-sitter/constant evaluator plus board variant headers; runtime evidence can be attached |
| `firmware_cross_check` | `{buildId, extractedPins, netlistSnapshot, policy}` | `{matches[], conflicts[], unknowns[], severity}` | ViBread rule engine; Arduino language/pin map and library metadata |
| `firmware_self_test_generate` | `{netlistSnapshot, boardProfileId, safetyLimits, fixtureProfile}` | `{snapshotId, sketch, testPlan, expectedJsonSchema, requiredFixture, safetyWarnings}` | ViBread generator; Arduino CLI compiles the resulting sketch |
| `firmware_artifact` | `{buildId, artifact:"elf"|"hex"|"diagnostics"|"report"}` | Stream/download by server-issued artifact ID plus SHA-256 and metadata | Job artifact store; never arbitrary filesystem reads |
| `firmware_upload` | `{buildId, boardProfileId, portHandle, approvalId}` | `{uploadId, resolvedPort, success, serialSessionHandle}` | Arduino CLI/PlatformIO upload, only after explicit hardware permission |

The first demo can implement `firmware_environment`, `firmware_compile`, `firmware_static_check`, `firmware_test`, `firmware_extract_pins`, and `firmware_cross_check`; self-test generation is still required for the physical-verification acceptance path, while upload should remain a separate permission-gated tool.

## 6) Integration notes and gotchas

### 6.1 End-to-end verification pipeline

1. **Freeze inputs.** Validate board profile/FQBN, supply voltage, MCU family, netlist snapshot, source snapshot, library lock, and test-spec schema. Resolve FQBN with `board listall`/`board details`; never silently fall back from Uno R4/ESP32/Pico to AVR.
2. **Install/verify toolchain.** In a job-owned data directory, verify the pinned CLI checksum/version, update indexes only in a serialized setup step, install the exact core and libraries, and capture `core list`, `lib list --format json`, and platform package versions.
3. **Compile.** Invoke Arduino CLI with `--json --warnings all --output-dir`; use a unique build directory. Require `success=true`, reject errors, preserve warnings, collect ELF/HEX/memory sections, and save `compile_commands.json`.
4. **Static checks.** Run Cppcheck against the same compilation database with `--platform=avr8` and skip third-party packages by default; run bounded clang-tidy only on portable project code; run Arduino Lint only for structure/metadata. Apply a deterministic severity policy and return all diagnostics with source spans.
5. **Static code/netlist cross-check.** Parse direct Arduino API calls, board variant mappings, bus initialization, library constructors, timer use, and direct register macros. Compare with netlist pins and expected direction/alternate function. `digitalWrite(variablePin, ...)`, callback-driven values, library-internal pins, and preprocessor-selected pins become `unknown`, not “pass”.
6. **Simulator tests.** Run deterministic host tests first, then MCU simulation. For simavr/avr8js, capture serial lines, GPIO transitions, timers/interrupts, and I2C/SPI transactions. For Wokwi, run a checked-in YAML scenario and record the token-backed run ID; do not make cloud simulation a hard requirement when no token is configured.
7. **Physical self-test/HIL.** Generate/compile a self-test sketch from the same netlist, flash only after ask-every-time/review/bypass permission, issue a reset, collect bounded newline-delimited JSON with a timeout, and classify failures as wiring/hardware/code only when evidence supports that attribution. Keep the user's normal firmware separate from the diagnostic firmware.
8. **Publish evidence.** Return a report containing immutable source/netlist/test/lock hashes, tool versions, diagnostics, artifact hashes, test cases, simulator mode/fidelity, cross-check confidence, and unknowns. Never claim “verified” when a test was skipped or dynamic pin use was unresolved.

### 6.2 Pin extraction: static first, runtime second

The Arduino language reference defines the high-level operations ViBread should recognize: `pinMode`, `digitalRead`, `digitalWrite`, analog I/O, PWM, and external interrupts ([language reference](https://docs.arduino.cc/language-reference/)). On Uno/AVR, direct code may instead use `DDRx`, `PORTx`, and `PINx`; `<avr/io.h>` selects device-specific definitions from `-mmcu` ([avr-libc IO documentation](https://avrdudes.github.io/avr-libc/avr-libc-user-manual/group__avr__io.html)). A practical extractor should:

* parse C++ syntax with `tree-sitter-cpp`, then evaluate literals, `constexpr`, `const int`, simple enum aliases, and one-level constant propagation;
* read the selected board's variant pin map from the compile profile, rather than hard-coding Uno numbers;
* recognize `Servo.attach(pin)`, `NewPing(trigger, echo)`, DHT constructors, NeoPixel constructors, SSD1306 `begin`/SPI constructor pins, and LCD/I2C bus setup as library-specific facts;
* record direct register expressions such as `DDRB |= _BV(DDB5)` as register-level usage and map them through the AVR header/board profile;
* preserve source spans and preprocessor branches; and
* emit unknowns for function-returned pins, dynamic arrays, runtime-selected buses, unmodeled library internals, and unsupported macros.

Static parsing cannot know which branches run or what an external sensor drives. For runtime evidence, simavr VCD/IRQ traces and avr8js `AVRIOPort` listeners can observe DDR/PORT/PIN effects, but only for exercised paths. A combined result should distinguish `declared`, `observed`, and `not_observed`; it must not turn absence of a trace into proof of safety.

### 6.3 Static analyzer setup

Cppcheck's AVR-aware invocation can be run directly:

```bash
cppcheck \
  --project=compile_commands.json \
  --platform=avr8 \
  --std=c++11 \
  --enable=warning,performance,portability \
  --xml --xml-version=2 \
  --cppcheck-build-dir=.vibread/cppcheck
```

PlatformIO equivalent:

```ini
[env:uno]
platform = atmelavr@5.3.0
board = uno
framework = arduino
check_tool = cppcheck, clangtidy
check_flags =
    cppcheck: --platform=avr8 --std=c++11 --enable=warning,performance,portability
    clangtidy: --checks=-*,bugprone-*,clang-analyzer-*,performance-*
check_skip_packages = yes
```

```bash
pio check -e uno --json-output --fail-on-defect=high --fail-on-defect=medium
pio run -e uno -t compiledb
```

PlatformIO's `pio check` options and tool configuration are [documented here](https://docs.platformio.org/en/latest/core/userguide/cmd_check.html); the `compiledb` target and optional toolchain include paths are [documented here](https://docs.platformio.org/en/latest/integration/compile_commands.html). Cppcheck itself warns that static analysis complements, rather than replaces, testing/dynamic analysis ([manual](https://cppcheck.sourceforge.io/manual.pdf)). `arduino-lint` should not be misclassified as a C++ analyzer: it checks sketch/library/platform/package structure, metadata, and Library Manager requirements ([scope](https://arduino.github.io/arduino-lint/latest/)).

### 6.4 PlatformIO alternative details

Current PyPI stable observed: **PlatformIO Core 6.2.0**, Apache-2.0 ([PyPI](https://pypi.org/pypi/platformio/json)). Useful commands:

pio run -e uno -t clean                # clean target

PlatformIO's package/core cache is convenient but should still be installed/updated in a serialized worker setup; use unique project/build directories for concurrent jobs.

### 6.6 Board-family changes

* **Uno R3/Nano ATmega328P:** `arduino:avr:uno` / the appropriate AVR Nano FQBN; `avr-gcc`, `avr/io.h`, Timer1/Timer2, 5 V electrical model, and simavr/avr8js are the expected baseline.
* **Uno R4 Minima/WiFi:** `arduino:renesas_uno:unor4minima` / `arduino:renesas_uno:unor4wifi`; RA4M1 Cortex-M4 at 48 MHz, 256 KB flash/32 KB RAM ([official Minima hardware page](https://docs.arduino.cc/hardware/uno-r4-minima), [PlatformIO board](https://docs.platformio.org/en/latest/boards/renesas-ra/uno_r4_wifi.html)). AVR direct-register code and simavr/avr8js do not apply; timer/PWM/ADC/EEPROM and boot/upload behavior need a Renesas-aware core/simulator/profile.
* **ESP32:** Arduino CLI FQBN depends on the Espressif board (`esp32:esp32:<board-id>`); PlatformIO uses `platform = espressif32`, `framework = arduino` ([PlatformIO Espressif32](https://docs.platformio.org/en/latest/platforms/espressif32.html), [Espressif Arduino core](https://github.com/espressif/arduino-esp32)). Account for 3.3 V, boot-strapping/flash pins, FreeRTOS/concurrency, and board-specific peripherals; AVR register and timer assumptions are invalid.
* **Nano RP2040 Connect / Pico:** Nano RP2040 Connect uses RP2040 dual-core Cortex-M0+ ([hardware page](https://docs.arduino.cc/hardware/nano-rp2040-connect)) and a different Arduino core/FQBN; PlatformIO's Pico board uses `platform = raspberrypi`, `board = pico` ([board docs](https://docs.platformio.org/en/latest/boards/raspberrypi/pico.html)). simavr is not applicable; use a board-specific simulator or host tests and label fidelity.

## 7) Risks, unknowns, and deterministic self-test design

### 7.1 Test-spec format the agent should write

Use a versioned, declarative JSON/YAML format owned by ViBread; do not let the LLM emit shell commands. Example:

```yaml
schema: vibread.test/v1
id: uno-led-button
board:
  fqbn: arduino:avr:uno
  core: arduino:avr@1.8.8
firmware:
  build_id: <server-issued-id>
fixture:
  netlist_hash: <sha256>
  required_parts: [led, 220R, button, 10kR]
  safe_voltage_v: 5.0
tests:
  - id: boot-ready
    reset: power_on
    timeout_ms: 3000
    expect:
      serial_json:
        - path: event
          equals: READY
  - id: button-drives-led
    stimulus:
      - set_input: {pin: D2, value: LOW}
      - wait_ms: 20
    expect:
      - serial_json: {path: state.led, equals: ON}
      - pin: {pin: D13, value: HIGH}
cleanup:
  - set_all_declared_pins: INPUT
  - serial_json: {event: TEST_DONE}
```

Required fields are `schema`, immutable snapshot/build IDs, board/FQBN, fixture/netlist hash, bounded timeout, deterministic reset, stimuli, expected observables, and cleanup. Allow only finite operations (`set_input`, `set_control`, `wait_ms`, serial match, pin/bus assertion, screenshot/VCD where supported). A test runner should reject unbounded loops, arbitrary code, unspecified pins, and expectations that cannot be observed in the selected mode. Use JSON Lines for device output with a monotonic `seq`, `test_id`, `event`, and `t_ms`; include a firmware build hash in the first `READY` event.
### 7.2 Deterministic self-test generation from a netlist

There is no mature generic “netlist-to-Arduino-self-test” library found. Existing prior art is fixture-specific:

* [Arduino cable tester](https://github.com/akiraNuma/arduino-cable-tester) (MIT, 1–5 wires) drives one TX HIGH and checks its matching RX HIGH while all other RX lines stay LOW; it requires 10 kΩ pulldowns and a fixed pin map.
* [AVR pin-test](https://github.com/RyuKojiro/avr-pintest) (MIT, small/low-activity) checks AVR pin shorts after soldering; it is not a netlist compiler.
* [Fubarino manufacturing test](https://raw.githubusercontent.com/fubarino/fubarino.github.com/master/sd/files/FubarinoSD_ManufactureTest.pde) is an instructive fixed test-jig sketch for opens/shorts/misconnections, but its project/license context is not suitable as a drop-in dependency **[UNVERIFIED]**.
* [Uno test shield](https://github.com/friets/arduinounotestshield) demonstrates a resistor-limited Uno pin fixture, but no license is visible in the repository page **[UNVERIFIED]**; do not copy it.
* Adafruit's MIT [CircuitPython BoardTest](https://github.com/adafruit/Adafruit_CircuitPython_BoardTest) shows a maintained board-test pattern (GPIO, UART, SPI, I2C, voltage, SD) but targets CircuitPython, not Arduino AVR.

ViBread's generator should be new code with this algorithm:

1. Partition netlist nets into **safe digital loopback candidates**, **bus/device probes**, **power/analog measurements**, and **un-testable/active** nets. Exclude MCU pins tied directly to VCC/GND, reset/clock/USB, active outputs, or unknown external voltage unless a declared resistor/fixture makes the test safe.
2. For each safe pair/net, initialize every involved pin as `INPUT` (no conflicting drivers), drive exactly one source HIGH then LOW through a declared current-limiting resistor, wait a fixed settle interval, and read the expected sink plus every forbidden sink. Restore `INPUT` after every case.
3. Generate both directions where the fixture permits, and test pull-up/pull-down behavior separately. Never drive two pins against each other without a resistor/current bound. Report `INCONCLUSIVE` when the net has only one observable MCU endpoint.
4. Generate bus-specific probes: I2C scan plus known device identity/register read where supported, SPI loopback only with a declared loopback fixture, ADC measurements only through a declared divider/range, and display readback/screenshot only when the simulator/device supports it.
5. Emit deterministic serial JSON with case IDs and expected values; compile the self-test with the same pinned board/core; run it in simulation when the model supports it; then run on hardware only with explicit permission.

The ATmega328P datasheet says ports are tri-stated during reset and defines per-pin/port electrical characteristics ([Microchip datasheet](https://ww1.microchip.com/downloads/en/DeviceDoc/Atmel-7810-automotive-microcontrollers-ATmega328P_datasheet.pdf)). A self-test cannot safely or reliably detect every physical fault: shorts to power, an external module actively driving a net, insufficient resistor/current limits, hidden breadboard rails, analog leakage, and unpowered back-power paths can all produce false pass/fail or damage hardware. The primary physical-verification result must include `PASS`, `FAIL`, or `INCONCLUSIVE` plus the fixture/safety assumptions; never reduce an unknown to a green check.

### 7.3 Attribution and permission risks

* **Design vs code vs wiring:** a compile failure is code/toolchain; a simulator failure under a correct diagram is code/design; a self-test mismatch with a compiled known-good diagnostic sketch is wiring/hardware only when the fixture is valid. Keep attribution probabilistic when a module model is incomplete.
* **Dangerous operations:** installing cores/libraries mutates shared state; compile hooks may execute project scripts; upload/reset can damage connected circuits. Permission modes should map to `read-only`, `compile`, `simulate`, `upload`, and `serial-write`, with upload/serial-write requiring an approval ID.
* **Untrusted generated source:** run compilers/analyzers in a container or restricted worker with no network after dependency resolution, resource limits, no host filesystem access, and bounded stdout/stderr. Keep `arduino-cli`'s GPL notices/source obligations separate from ViBread code; do not embed its Go package without a deliberate license review ([official integration source notes GPL](https://arduino.github.io/arduino-cli/1.5/integration-options/)).
* **MCP security:** existing “raw CLI command” servers are not acceptable as the ViBread server. Fixed argv and allowlists are mandatory; use server-issued workspace/artifact IDs, never return arbitrary absolute paths, and redact serial data/secrets before agent context.
* **Simulator fidelity:** Wokwi scenarios are alpha and cloud-dependent; simavr is GPL/Linux-only; avr8js supplies CPU/GPIO but not external hardware models. Record mode, simulator version, unsupported peripherals, and whether a test was actually run.
* **Version drift:** Arduino Library Manager and PlatformIO registries are mutable. Keep a lock manifest and archive exact `library.properties`/checksums. Re-run license checks before submission; NewPing's custom “use as-is” terms and LiquidCrystal I2C's missing license are immediate red flags.

### 7.4 Recommended weekend cut line

Ship Arduino CLI v1.5.1 + Uno AVR core compile/JSON parser + exact library lock + Unity host tests + one simulator adapter + static pin extraction/cross-check + generated safe GPIO self-test + structured MCP tools. Make PlatformIO optional for native tests/static checks and Wokwi optional when a token exists. Do not spend the critical path implementing every board family, a full C++ semantic analyzer, or a generic serial shell.
